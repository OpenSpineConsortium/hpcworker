"Beethoven" means the browser extension of that name (the "Extension"), the small helper program
that ships inside the Extension for you to install on your computer and that carries the Extension's

5. WHAT BEETHOVEN DOES WITH YOUR CREDENTIALS AND YOUR WORK

This section describes the software as shipped, so that you can hold Licensor to it.

(a) Claude. Beethoven never reads, stores, copies, prints or relays a Claude credential. You sign in
to Claude Code yourself, through Anthropic's own flow, once, in a terminal on a compute node of your
own cluster account. The Extension starts that terminal for you, in the same command that starts
your worker, through your portal's shell or, on the ssh path, through a connection you signed in to
with your cluster password and code (the key of section 5(b)(iii) can never start it), opens
Anthropic's sign-in page in a new tab, shows you one box, and closes that tab once Claude Code
reports you are signed in, unless the tab has loaded another page since you pasted the code; you
sign in on Anthropic's page and paste the one-time code it shows into that box. The Extension types
the code once into that terminal and keeps no copy of it: it is not stored, not written to the audit
log and not sent to Licensor or anyone else, and the Extension never reads Anthropic's page or your
clipboard to obtain it. Claude Code makes its credential from the code and keeps it in its own
folder in your cluster account; the Framework only starts Claude Code where that credential already
is, and Beethoven reads Claude Code's own report of whether it is signed in, with the account and
plan that report names, nothing more. You use one Claude account, your own. You answer Claude Code's
one-time question about Remote Control yourself, with the box you tick in the Extension's panel
before your first worker starts; the Framework records that answer in one file in your cluster
account when you press Connect, and your worker gives it to Claude Code when Claude Code asks. Trust
for the worker's own folder is recorded in Claude Code's settings by the Framework when a worker
starts. Beethoven gives Claude Code no answer you have not given.

(b) Your sign-in to your cluster. The Extension reaches your cluster in one of two ways and tries
the first before the second: the ssh path, which needs no VPN, and the portal path, which may need
your institution's VPN (at Wayne State, GlobalProtect). It never signs in to Claude for you on
either path (see (a)). The ssh path is new in this version and has been tried only against ssh
servers that Licensor ran itself, set up like your institution's, not yet with a real account on a
real cluster.

(i) The Bridge. A browser extension cannot open an ssh connection by itself, so the ssh path needs a
bridge that carries the Extension's encrypted connection to your cluster's ssh port and back. In
this version that is the Bridge: a small helper program that ships inside the Extension, which you
install once on your computer, in your own user account and without administrator rights, by saving
the installer the Extension offers you from its own package and running it (the Extension cannot run
a program for you). Your browser starts the Bridge only when the Extension asks for it, and the
Bridge ends when the Extension lets it go. The Bridge opens a network connection only to your
cluster's ssh port (at Wayne State, grid.wayne.edu, port 22, and another address only if its
installer wrote one into its settings), carries bytes both ways without reading, keeping or logging
them, holds no password, key or other credential, offers no shell and runs no other program. The
uninstaller placed beside it removes it. The Extension can also carry the ssh path through a relay
server, but only one that your institution's site profile names; none is named in this version, and
if one ever is, the privacy statement will name who runs it and what it sees before any version uses
it. If no Bridge is installed and you do not install one, or your cluster's ssh port cannot be
reached from your network, the Extension uses the portal path.

(ii) Your password and code. The first time you use the ssh path in this browser, again whenever the
key of (iii) is missing or refused, and when you sign in to Claude on the ssh path (see (a)), the
Extension asks you to sign in on its own sign-in sheet, a page of the Extension: your account name,
your cluster password and, where your cluster asks for one, the one-time verification code from your
authenticator app (at Wayne State, Google Authenticator). The Extension sends them only to your
cluster, inside the encrypted ssh connection, after your cluster's identity (its host key) has
matched the one the Extension carries for it, and only for that sign-in. It never stores them, never
writes them to a log, never offers to remember them, and never sends them to Licensor or anyone
else. It never makes a verification code and never holds the secret your authenticator app keeps. If
your cluster refuses a code with words that may mean a mistyped code or no verification code set up,
the Extension asks you which, and only if you say you have none does it show you your institution's
own instructions for setting one up, which you follow yourself, on your institution's pages;
Beethoven takes no part in that step. After your first sign-in on the sheet, the Extension keeps
that signed-in connection open, in your browser's memory only, for up to ten minutes, so that your
first Connect can run the Claude sign-in of (a) in it without asking for your password and code
again; it closes when that sign-in ends, when the ten minutes pass, when you cancel, or when your
browser closes, and nothing of it is stored.

(iii) The key in your browser. In that sign-in the Extension makes a key in your browser and runs
the Framework's browser-key step in your cluster account, which adds one line to your account's
~/.ssh/authorized_keys file. That line lets the key run only the Framework's gate: a fixed list of
short commands that report the Framework's version and your account name, start a worker without any
Claude sign-in, read your worker's state and its own named files, stop it, mark its workspace
restricted, and remove the line itself, within limits on how many workers it may name and how often
it may start one. Through that line the key gets no terminal, no other command, no file transfer and
no forwarding, and the gate can never sign a worker in to Claude. Later connections from this
browser sign in with the key and ask you for nothing. The key's private half never leaves your
browser and is never sent to Licensor. By default it is stored encrypted under a second key that
your browser keeps and lets no page or script copy out, and Beethoven uses it without asking you;
both are stored with the Extension's data in your browser profile on this computer, so someone who
can use that browser profile, or read your computer account's files, could use the key, within the
limits of that line. If you choose, Beethoven instead keeps the key encrypted under a secret that
only your passkey releases (Windows Hello, Touch ID, or your device's PIN or password), so that it
cannot be used until you unlock it, once each time you open your browser. That protection is off
unless you turn it on, on the sign-in sheet, when Beethoven offers it once after setup, or in
Settings, and you can turn it off again in Settings. Turned on later, it protects the key from then
on; for a while your browser's own files may still hold the earlier form, until the browser tidies
its database, so if you want the protection from the start, choose it on the sign-in sheet. Your lab
may set the line to lapse after a number of days, after which the Extension asks you to sign in with
your password and code again.

(iv) Forgetting this computer. "Forget this computer", in the Extension's Settings, deletes the key
from your browser and asks your cluster, through the gate, to remove its line. If your cluster
cannot be reached, or the key is protected and you do not unlock it, the Extension says so, and the
line stays until it is removed, which the command "hpcworker browser-key remove", run in a terminal
on your cluster, does. The line is what lets the key in: once it is gone from your cluster, a copy
of the key left anywhere is of no use. Withdrawing your approval under section 3 does not remove the
line; Forget this computer or that command does. In this version your account keeps one such line:
signing in over ssh from another browser replaces it, and the key of the browser you used before
stops working. Uninstalling the Extension deletes the key from your browser but cannot remove the
line from your cluster, so use Forget this computer first. A passkey you made under (iii) is kept by
your system or your browser's password manager, not by the Extension: Forget this computer asks it
to drop the passkey, and where it does not, you delete it there.

(v) The portal path. The Extension uses the sign-in your browser already holds for your
institution's Open OnDemand portal, on that one website only, from its own background and without a
portal tab where your browser allows it. It never reads that sign-in, never reads, stores or types a
portal password, never signs in for you and never touches a multi-factor step. When the portal asks
for a sign-in, the Extension opens the portal in a tab for you to sign in there (in your browser's
own sign-in box, or on the portal's own sign-in page), never sees what you type there, and closes
that tab once you are signed in, while it is still on the portal. Where your portal does not share
its sign-in with the Extension, it keeps that tab behind your other tabs until the work in hand is
done and then closes it, and for a later action opens the portal in a background tab and closes it
again. The one thing it reads about you from the portal is your account name, from the portal's own
dashboard page. If your portal's shell asks for your cluster password, as it may for an account that
has no key on the cluster, the Extension types nothing there and offers a one-time step instead: it
opens the portal's own terminal page in a tab, and you type your password there yourself; the
Extension never sees it. Once you say you are in, or the page's title shows that your shell is up,
the Extension types one line into that terminal (or leaves it on your clipboard for you to paste),
which runs the Framework's login-setup step in your own account. That step makes a key in your
cluster account, in its ~/.ssh folder, that opens your account only from the computer the terminal
came from, which at your institution is its Open OnDemand server (it is a file in your own account,
protected as your other files are, and hidden from Claude Code inside your worker; anyone who
obtained it and could connect from that server could use it), and has ssh offer it when the portal's
shell connects you, so that the shell need not ask for your password; it never reads, changes or
prints a key you already have. The key stays in your cluster account: the Extension never sees it,
keeps nothing about it in your browser and sends nothing about it to Licensor. The command
"hpcworker login-setup --remove", run in a terminal on the cluster, removes it. This step has been
tried only against the Licensor's mock portal, not yet on a real cluster by an account without a
key.

(c) Your account name, as your cluster confirmed it, and the answer of the last approval check with
its time are stored in the Extension's own storage in your browser. Nothing about your approval is
copied to your cluster account; the Framework has no key, password or account list of Licensor's.

(d) The Framework makes a random token for each job so that only your own browser session can reach
your worker. It is kept in a file only you can read, is never shown, and never appears on a command
line or in a job log.

(e) Where your work goes. Files the worker reads and every command's output are sent to Anthropic.
While you are connected through claude.ai the transcript is also stored on Anthropic's servers. A
personal plan is retained five years if model training is on and 30 days otherwise. No BAA covers a
personal plan. FERPA records, IRB data and export-controlled technical data must not be in the
working directory. Remote Control usage draws from your plan's shared limit. The Extension shows
these sentences in short form, with the full text one click away, before your first worker starts,
and a one-line reminder beside Connect each time you start one, and does not start a worker in a
folder you have marked restricted.

(f) The Extension runs no code on claude.ai or any other Anthropic page and reads nothing from them.
It runs no page script on the ssh path. Its only page script runs on the one portal website you
connect, on the portal path: where your portal does not share its sign-in with the Extension, to
carry the Extension's requests there, and, during the one-time step in (b)(v), on the portal's
terminal page, where it watches only the page's title and types only the one line described there.
It opens an Anthropic page only in a new tab, as a bookmark would: the sign-in page during the
sign-in described in (a), your worker's session page when a worker you started is ready (unless you
turn that off) and when you choose "Open my session" or "New session", the connectors settings page
if you choose the optional Google Drive step, and the plans page if you follow "See plans" on the
welcome page; it closes the sign-in tab it opened once you are signed in, and it may bring forward a
claude.ai tab it opened itself. Of an Anthropic tab it opened, it learns only that the tab has begun
loading a page, which the browser tells it without the page's address or content.

(g) Of (a) to (f), only your account name in (c) is sent to Licensor, in the approval check that
section 10 describes; nothing else is. Section 10 describes the only things that may be.

10. WHAT LICENSOR RECEIVES, ACCESS RECORDS AND PRIVACY

(a) The approval check. Only after you have accepted this agreement, and only once your cluster has
accepted your sign-in and your account name is known, the Extension asks Licensor's access service
(https://beethoven-access.openspineconsortium.workers.dev) whether that account is approved: when
you first sign in to your cluster after accepting this agreement, about once a day while it is in
use, and again when you open the Extension's panel after a day has passed or after a no. Each check
sends, over an encrypted connection and without cookies, your account name as your cluster confirmed
it, your portal's hostname (on the ssh path, the hostname of the portal your institution's site
profile names), the product name, the Extension's version, the installation identifier of section
3(e) and, as any request does, the time it was made. The service answers yes or no, and for a no may
say that your account is bound to another installation, that this installation is bound to another
account, or that the version is too old. Licensor's service keeps one record of the checks for each
account and product: the account name, the product, the portal's hostname and the version of the
latest check, when the account was first and last checked, how many checks there have been, the
answer of the latest check and the reason given with a no, when the answer last changed, and a
salted hash of the network address of the latest check (never the address itself); it also counts
each day's checks per account and per hashed address, to limit them, and deletes those counts after
two days. For each approved account it also records the installation identifier the account is bound
to, with the product, the version and when that installation first and last asked, and for that
installation the account it is bound to; and, when a check is refused because of another
installation or another account, how many times and when the first and the last time were, with the
first eight characters of a one-way hash of the refused installation's identifier. When another
installation asks about your account, Licensor is told by e-mail, at most once a day per account,
with a link that can move your approval to that installation. The Extension keeps a yes for up to a
day, and for up to seven days when the service cannot be reached, so that an outage on Licensor's
side does not stop your work; it keeps a no for ten minutes.

(b) Two files. Once a day, and only after you have accepted this agreement, the Extension also
fetches from Licensor's website a small file naming the address of the access service
(https://openspineconsortium.com/beethoven/services.json) and a signed list of withdrawn versions
(https://openspineconsortium.com/beethoven/killlist.json). Those requests are sent without cookies
and carry nothing about you beyond what any web request carries (your network address). The check
in (a) and these two files are the only requests the Extension makes to Licensor.

(c) The Extension sends no error reports, no crash reports and no usage data, and there is no
activation step: it has no code for them and no address to send them to. Your acceptance record (the
