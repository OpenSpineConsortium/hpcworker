# Ashley Bridge: architecture

Distilled from the research report's "Build specification for the week of 28 September 2026"
(`RESEARCH_REPORT.md`). Where this document and the report differ, the report governs; where the
report is silent, the fact is marked not yet measured. Written for the engineers building the two
streams and for a research-computing or security office reading what the pieces do.

The one-sentence design: the student's own Claude Code runs as a batch job on the cluster and
registers itself with Anthropic through Claude Code Remote Control; the browser extension only starts,
watches and stops that job through the student's existing Open OnDemand session, on one origin.

## 1. Components and what each reuses

| Component | What it is | Reused from Ashley 2.0.0 | New here |
|---|---|---|---|
| Framework (`framework/`, `hpcworker`) | Shell plus Python installed in the student's home or group volume: site profile, scheduler/runtime/egress adapters, job template, worker entrypoint, probe job | `grid/worker.sbatch.tpl` and `grid/bootstrap.sbatch` (the sbatch wrapper, the Apptainer sandbox recipe on a Node 22 base, node-local temp and cache with a cleanup trap, `/dev/shm` IPC, the Slurm executable wrappers inside the container, `.part`-then-rename file writes) | Site profile schema; adapter modules (Slurm first, PBS Pro and LSF next); egress probe; Remote Control launcher in `tmux`; per-job token; `status.json` and `connection.json` writers; the `XDG_RUNTIME_DIR` fix |
| Worker image | A SIF built once from a Debian 12 or Ubuntu 22.04 base with the native installer pinned to a version; `DISABLE_AUTOUPDATER=1`; Claude Code's config directory (the profile's `claude_config_dir`; `~/.claude` by default, `$HOME/.ashley/claude` on Wayne State) bind-mounted from persistent storage, never baked in | The sandbox recipe | SIF form for parallel-filesystem sites; `--fakeroot` rung detection |
| Extension (`extension/`, `ood-worker`) | WXT plus TypeScript, `browser.*` with Promises, `minimum_chrome_version` 148; one codebase for Chrome, Edge, Firefox and Safari | The signed-key licence gate (`grid/license.js`: `ASHLEY1.<b64url payload>.<b64url sig>`, Ed25519, revocation list `ASHLEYREV1`, public keys `k1` and `trial`); the clickwrap text and acceptance record (`core/terms.ts`, `vscode/termsPanel.ts`); the diagnostics node model (`core/diagnostics.ts`: `id`, `title`, `dependsOn`, `assumption`, `check`, `repair`, `manualFix`, `futureRisk`) | Portal-origin content script; Shell WebSocket driver; Files and Active Jobs clients; side panel (Chrome/Edge), `sidebar_action` (Firefox), popup (Safari); on-device audit log; kill-list verifier |
| Licence and access service | Ashley's existing activation endpoint, plus a signed JSON document carrying revocations and the kill-list, served over HTTPS | Key issuance, AccessID binding, merchant of record | Kill-list signing key under hardware-key custody; daily fetch |
| Partner-site package (optional) | An Open OnDemand Interactive App (`form.yml`, `submit.yml.erb`, `template/script.sh.erb`) that launches the same job template, for campuses that will install it | The job template | The `form.yml` and `view.html.erb` |

Two things are deliberately absent (report, "Components and what each reuses"): any code on claude.ai
(no content script, no host permission, no fetch patch), and any handling of a Claude credential (no
`setup-token`, no `CLAUDE_CODE_OAUTH_TOKEN`, no read of `~/.claude/.credentials.json`, no multi-account
rotation). What is carried over from Ashley's `grid/phone.js` is the behaviour, not the code: run
`claude remote-control` in a pseudo-terminal, strip every credential variable and
`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` from its environment, take the one-time consent only from
the student's own recorded answer (Claude Code's `remoteDialogSeen` key, section 4.1; a marker file
the student wrote is the fallback), restart with backoff, parse the session name and link, and never
run `claude auth logout` (it would revoke the login).

Wayne State's profile carries `reqp` with `--qos=requeue`, `gmsap` and `gvohp` for GPU work, the

report's list. Additions: `site` and `display_name`; `qos_cpu` and a separate `partition_cpu_batch`

measured egress result kept under `egress.measured` with its date and node. The profile is the one
place a site's facts live; the probe job corrects it and the templates render from it.

## 3. The adapter interface

The report's headline calls it a six-call adapter; its specification table lists eight calls plus a
two-call egress adapter, and the table governs. Each call is a single command template plus an id or
status regex, delimited text first and JSON second, because status JSON is version-gated on every
scheduler (Slurm from 21.08, PBS Pro's `-F json`, LSF's `-json` only with `-o`).

| Call | Slurm | PBS Pro | LSF | Contract |
|---|---|---|---|---|
| `detect_scheduler()` | `command -v sbatch` | `qsub` present and `qstat -F json` succeeds | `bsub`, `bjobs` | family or `unknown`; under 1 s of login-node CPU |
| `detect_runtime()` | `command -v apptainer singularity podman enroot`; `module -t avail`; `srun --help \| grep container-image`; `sysctl -n user.max_user_namespaces` | same | same | runtime, module, predicted fakeroot rung; never runs a container on the login node |
| `submit(script) → id` | `sbatch --parsable` (id before `;`) | `qsub` (bare id) | `bsub` ("Job <N> is submitted") | one call; 0.5 to 1 s between calls |
| `status(id) → {state, node}` | `squeue -h -j <id> -o '%T\|%N'`, then `sacct -P -j <id> --format=State,NodeList` | `qstat -f -F json <id>` (`-x` when finished) | `bjobs -noheader -o 'jobid stat exec_host'` | normalised to `PENDING`, `RUNNING`, `DONE`, `FAILED`, `UNKNOWN`; called only by the probe and the bootstrap, never in a loop |
| `cancel(id)` | `scancel` | `qdel` | `bkill` | idempotent |
| `attach(id)` | `srun --jobid=<id> --overlap --pty bash` | `ssh <node>` | `ssh <node>` | best-effort diagnostic; a site may forbid it |
| `node_tmp()` | `$SLURM_TMPDIR`, then `$TMPDIR`, then `/scratch/$USER/job_$SLURM_JOB_ID`, then `/tmp` | same | same | resolved inside the job; the profile's `node_tmp_var` overrides the order |
| `runtime_exec(image, cmd, binds, env)` | `apptainer exec --bind <shared_state_dir>,<ipc_dir>,<home>/.claude --env ...` | `podman run --rm -v ...` | `srun --container-image` | propagates `https_proxy`, `no_proxy`, `NODE_EXTRA_CA_CERTS` explicitly; sets `DISABLE_AUTOUPDATER=1`; never sets `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, `DISABLE_GROWTHBOOK`, `ANTHROPIC_BASE_URL` or `CLAUDE_CODE_OAUTH_TOKEN` |

Egress adapter: `egress_probe()` runs inside the probe job and returns the class plus the working proxy
environment by testing `https://api.anthropic.com/`, `https://platform.claude.com/` and
`https://claude.ai/` with and without the inherited variables (only HTTP CONNECT proxies count; Claude
Code refuses SOCKS, so an `ssh -D` tunnel is unusable); `egress_env()` renders the variables the job
template exports into the container. Two traps from the report: Open OnDemand submits with
`--export=NONE` by default, which strips a login-set proxy from the job, so the variables are injected
explicitly; and an allowlist holding only `api.anthropic.com` passes a pre-authenticated worker and
fails a fresh login, because token exchange goes to `platform.claude.com`.

The framework also enforces a task manifest independently of the agent (report, "Security controls"):
working directory, allowed partitions, allowed egress hosts; input data read-only with a separate
writable working directory; scheduler polling never faster than the profile's floor.

## 4. The job template and the Remote Control launch sequence

### 4.1 The one-time step, in one sitting (the student's answers, not the tool's)

`hpcworker claude login`, typed once in the portal's Shell tab, asks the scheduler for a short
allocation on the CPU partition (never the login node) and, inside the worker image:

1. runs `claude auth login`, paste-code flow. The credential lands in
   `<claude_config_dir>/.credentials.json` (on Wayne State `$HOME/.ashley/claude`, Ashley's
   `CLAUDE_CONFIG_DIR`), mode 0600, readable only by the student. Measured on Wayne State 2026-09-28:
   the paste-code login completed from a compute node inside the image; `claude auth status` reported
   `loggedIn: true`, plan `max` (that login was lost with its folder later the same evening;
   `SECURITY.md`, incident record).
2. then, if Claude Code has not yet recorded the student's answer, runs `claude remote-control` once
   in the worker's workspace, so the student answers `Enable Remote Control? (y/n)` (and the trust
   question if it is asked), sees the registration block, and presses Ctrl-C, in the same sitting. No
   separate consent command is needed; `hpcworker claude consent` remains as an alias that explains
   this. The workspace, not `$HOME`, is where the trust answer is saved: trust is never saved for
   `$HOME`, and the question would return on every run.

The consent signal is Claude Code's own. Claude Code records the answer in
`<claude_config_dir>/.claude.json` as `remoteDialogSeen: true` (alongside a `remoteControlMachineId`),
and directory trust as `projects[<dir>].hasTrustDialogAccepted: true`. The framework reads those two
boolean keys and nothing else from that file; a marker file (`consent_markers` in the profile) is only
a fallback. The framework never rewrites that file except to seed `hasCompletedOnboarding`, `theme`
and the workspace's `hasTrustDialogAccepted`, and only when the student has started a login or a
worker on purpose; a status check writes nothing.

The extension guides this with text and checks afterwards (checks 13 and 14); it never types the
answers. Remote Control requires a full-scope login: `setup-token` and `CLAUDE_CODE_OAUTH_TOKEN`
credentials can only make model requests, and a `CLAUDE_CODE_OAUTH_TOKEN` in the environment outranks
the stored login and would silently disable Remote Control in any process that inherits it. This is why
Ashley's earlier `setup-token` capture is gone rather than supplemented.

### 4.2 The job template

One file rendered from the profile.

Header directives: `--partition`, `--qos`, `--account`, `--time`, `--tmp`, `--requeue`,
`--signal=B:TERM@120`, `-D <shared_state_dir>/<run>` (so `--output` resolves where intended); a
successor in the always-on chain (below) is the same rendered file submitted with
`--dependency=afterany:<predecessor>`.

Fixed body, in order:

1. `cd $(node_tmp)`; stage the SIF to node-local storage if the profile says so. Node-local temp and
   the runtime's cache (`APPTAINER_TMPDIR`, `APPTAINER_CACHEDIR` and the `SINGULARITY_` twins) sit
   under the node's local disk with a cleanup trap; nothing of ours goes under a login node's `/tmp`.
2. Export the egress environment from `egress_env()`.
3. `mkdir -p /dev/shm/$USER/xdg && export XDG_RUNTIME_DIR=/dev/shm/$USER/xdg` (the bash tool's
   `EACCES ... /run/user/<uid>` defect on nodes without systemd user sessions, closed "not planned"
   upstream; whether the fix holds is open question 5).
4. `JOB_TOKEN=$(head -c 32 /dev/urandom | base64)`, written with mode 0600 into the state directory,
   never on a command line or in the environment of a submitted job.
5. Write `status.json` with `state: starting`.
6. Start the Remote Control process (4.3).
7. Write `connection.json`: `session_name` (the line of the registration block that carries the
   name: `<site>-<jobid>` when Claude Code accepts `--name`, otherwise its generated one, of the form
   `asx10-hazy-meadow`), `environment_url` (`https://claude.ai/code?environment=env_...`, the link the
   extension's *Open in Claude* button opens), `host`, `port` if the optional `/rnode/` service is
   enabled, `pid`, `started_at`, `token_path`.
8. A `SIGTERM` trap that flushes `status.json` (`state: preempted`, `resume_hint`) and exits cleanly.
9. Before the wall time ends (at the `--signal=B:TERM@120` warning at the latest), queue exactly one
   successor: `sbatch --dependency=afterany:$SLURM_JOB_ID` of the same rendered script, its id
   recorded in the run directory so a second submission is refused. A stop file ends the chain: no
   successor is queued, and a successor that was already queued exits at once when it starts. The
   worker is always on until the student stops it; `afterany`, never `afterok`, so a predecessor that
   ends non-zero for a trivial reason does not strand the chain.

All persistence lives on shared storage; `/tmp` is treated as ephemeral; nothing runs on the login node
beyond the one `sbatch`. The job's cleanup trap removes only its own node-local temp and its `/dev/shm`
directory; the framework deletes nothing outside its own run directories (`SECURITY.md`, the incident
of 2026-09-28). Compared with Ashley's `worker.sbatch.tpl`, what changes is the payload
(`claude remote-control` in `tmux` instead of the inbox daemon) and the status files; what stays is the
`/dev/shm` scratch bound to `/tmp`, the `--signal=B:TERM@120`, `--requeue` with `--open-mode=append`,
the read-only bind of the host's Slurm client into the container, and the refusal to start when a piece
is missing.

### 4.3 The batch launch

```
tmux new-session -d -s rc \
  "apptainer exec <binds> <image> claude remote-control --name '<site>-<jobid>' \
     --capacity <N> --permission-mode default 2>&1 | tee -a <shared_state_dir>/<run>/rc.log"
```

then a loop that waits for the registration line in `rc.log`, writes `connection.json` and sets
`status.json` to `state: online`. `tmux` supplies the pty the trust check requires ("when its standard
input or output isn't a terminal, the command can't ask and exits with a `Workspace not trusted`
error") and detaches the process from the job's lack of a controlling terminal; `script -qfc` is the
fallback, and is what Ashley's `phone.js` uses today. Supervised mode (`--permission-mode default`) is
the default so every command is approved from the app, which is what Utah, NERSC and USC require of
agents on their systems; a student may choose a broader mode knowingly.

The registration block of Claude Code 2.1.283, after the QR code, is what the loop parses:

```
·✔︎· Connected · phone · HEAD
    Capacity: 1/32 · New sessions will be created in the current directory
    asx10-hazy-meadow
Continue coding in the Claude mobile app or https://claude.ai/code?environment=env_01XzAN32jsbL8W1PAFSvitBt
Or ask Claude to work in this folder from your projects on claude.ai
```

The name line and the `https://claude.ai/code?environment=...` URL go into `connection.json` as
`session_name` and `environment_url`. The environment id is stable per machine id, so a second host on
the same login joins the same environment. The extension shows a green *Open in Claude* button that
opens `environment_url` in a new tab with `browser.tabs.create` (which needs no `tabs` permission and
puts no code on claude.ai) and a *Copy link* button; it still names the session for students who
prefer to pick it at claude.ai/code or under *Code* in the Claude app. No QR code is needed.

The worker is always on. The successor queued with `afterany` reconnects the same session:
`claude remote-control --continue` in the same directory when `connection.json` is younger than four
hours (the documented recovery window), else a fresh registration, which lands in the same
environment. Whether `--continue` survives a Slurm requeue is open question 4. If `rc.log` shows the
full-scope-token error, the extension tells the student to run `hpcworker claude login` again and does
nothing else: a Remote Control session that outlives the login stops making progress.

Whether `claude remote-control` stays registered from an `sbatch` job at all was open question 1. It
was answered yes on 2026-09-29 (02:22 UTC): Ashley's phone host, Slurm job 40496445 on `asx15`, `sbatch` under a
pseudo-terminal with the student's answer already on record, registered and served a session opened
from the phone (`OPEN_QUESTIONS.md`). Before that no published account showed it under `sbatch`; the
launch sequence had been inferred from documented TTY behaviour and a community report of it working
over SSH plus `tmux`.

Session lifetime is the Slurm wall time. Server mode gives up after roughly ten minutes of network
outage and exits; the framework restarts it with backoff while the job lives.

## 5. The Open OnDemand channels

Open OnDemand has no public API: no release through 4.2.5 ships one, and the maintainers say the
endpoints are internal and not on the roadmap to open. The extension therefore rides three surfaces
chosen for stability across tagged versions 2.0.32 to 4.2.5 (report, "Open OnDemand gives three
channels everywhere"), plus an optional fast path. All portal traffic passes through one chokepoint
function in the extension that appends an audit record and enforces the poll floor.

| Purpose | Endpoint | Protocol | Browser context | Notes and failure signatures |
|---|---|---|---|---|
| Session check and PUN warm-up | `GET /pun/sys/dashboard/` | HTTPS, follow redirects | either | 302 to the IdP, a VPN captive page or a connection error means "sign in to your portal (and connect the VPN) in a tab"; never automate login. A cold per-user NGINX answers with a redirect to `/nginx/init?redir=...`, which loses a POST body, so warm up before writing |
| Bootstrap shell: submit the job, read the id | `GET /pun/sys/shell/ssh/<host>` (scrape `csrf=` from the inline script), then `wss://<ood>/pun/sys/shell/ssh/<host>?csrf=<token>` | WebSocket, no subprotocol; send `{"input": "..."}` and `{"resize": {...}}`; receive raw PTY text frames | content script on the portal origin (a service worker is also admitted because a non-`http` Origin skips the check, but Firefox and Safari cookie behaviour makes the content script the only safe choice) | Scrape the token seconds before connecting (the secret is per Node process; Passenger kills an idle app after 300 s). Close code 3146 with reason "No clusters defined.", "Invalid Origin.", "Bad CSRF Token." or `Host "<host>" not specified in allowlist or cluster configs.`. Defaults: 5-minute idle, 1-hour maximum. Run `sbatch --parsable <script>` once, parse the id, `exit`, close. Validate every frame as JSON: a bad frame throws inside the user's only shell process. The CSRF token travels in the query string and hence into access logs |
| Write request and control files | `PUT /pun/sys/dashboard/files/fs/<abs path>` (body = content; `?dir=true`; `?touch=true`) | HTTPS PUT with `X-CSRF-Token` from `<meta name="csrf-token">` | content script only (the Rails Origin check rejects `chrome-extension://`) | 422 = stale token or wrong Origin; 403 = allowlist or `EACCES`; 302 to `/nginx/init` = cold PUN, body lost. Gated by `upload_enabled`, `OOD_ALLOWLIST_PATH` and a 10 GB cap |
| Poll worker state | `GET /pun/sys/dashboard/files/fs/<shared_state_dir>/<run>` with `Accept: application/json` | HTTPS GET | either (service worker on Chrome/Edge; content script on Firefox/Safari) | Read `status.json`, `connection.json`, `rc.log` via `download_url` or `?download=1`; served `Cache-Control: no-store`; `files_upload_path` present if and only if uploads are enabled. File reads touch no scheduler, so they may run on a timer of seconds; the extension still uses the alarms floor |
| Upload a file to the working directory | `POST /pun/sys/dashboard/files/upload/fs` (multipart: `parent`, `name`, `file`) | HTTPS POST + CSRF | content script | 413 above `client_max_body_size`; 404 if uploads disabled |
| Job state | `GET /pun/sys/dashboard/activejobs.json?jobcluster=all&jobfilter=user` | HTTPS GET | either | `data` is an array of arrays (one inner array per 3,000-job slice); match `pbsid`; `errors` names unconfigured clusters. Reconciliation only; the primary state is `status.json` |
| Cancel | `DELETE /pun/sys/dashboard/activejobs?cluster=<id>&pbsid=<job>` (or `scancel` through the bootstrap shell) | HTTPS DELETE + CSRF | content script | redirects on success |
| Optional: Job Composer submission | `POST /pun/sys/myjobs/workflows.json`; `PUT .../workflows/:id/submit.json` (204); `GET .../workflows/:id.json` (`status`) | JSON | content script | deprecated in 4.1, gone in 5.0; 404 if hidden; "There are no configured hosts" if no clusters. Not relied on |
| Optional: partner-site Interactive App | `POST /pun/sys/dashboard/batch_connect/sys/<app>/session_contexts.json` (204); then `~/ondemand/data/sys/dashboard/batch_connect/db/<id>` and `.../output/<id>/connection.yml` via Files | JSON + Files | content script | requires the admin-installed app; a user can install nothing under `/var/www/ood/apps` |
| Optional fast path to the worker | `https://<ood>/rnode/<node>/<port>/<path>` (or `/node/...` with the worker mounted under that prefix) | HTTPS / WSS | either; the worker authenticates with `X-Job-Token: <JOB_TOKEN>` in a header or body, never `Authorization`, never the OIDC cookie, never `X-Forwarded-User` | 404 = proxy not enabled or `host_regex` mismatch; 503 "Failed to connect to <host>:<port>" = enabled, no listener; Set-Cookie is rescoped to `Path=/rnode/<host>/<port>`; avoid protocol-relative redirects. Since 4.1 the portal strips `mod_auth_openidc_session*` cookies and `Authorization`/`OIDC_*` headers before proxying |
| Detect-only | `/nginx/init?redir=`, `/nginx/stop`, `/logout` | HTTPS GET | none | recognised in redirects; never called; `/logout` never |

Which context talks to which endpoint is decided by cookies and CSRF together. Chrome and Edge send
the portal cookie from the service worker once the host permission is granted, unless third-party
cookies are blocked; Firefox and Safari have no documented guarantee. A content script on the portal
origin sidesteps the question, because content scripts initiate requests on behalf of the page's
origin, and it is the only context whose `Origin` passes the dashboard's
`protect_from_forgery with: :exception` for `PUT`, `POST` and `DELETE`. The rule: every write and the
shell bootstrap run from the portal-origin content script with the page's `X-CSRF-Token`; polling
GETs may run from the service worker on Chrome and Edge; Firefox and Safari use the content script for
everything.

The session the extension inherits lasts, with Open OnDemand's defaults, 8 hours of inactivity and
8 hours maximum; the cookie is HttpOnly and SameSite=Lax; a 302 to an identity provider or a 401
means "sign in again in a tab", and nothing is cached across the re-login.

The shell is a login-node shell. It is used only to open, run one `sbatch --parsable`, read the id and
close. Anything that keeps a login-node process alive for the extension's benefit breaks both the
shell's timers and every login-node policy sampled (Wayne State's 20-process cap with immediate
deletion; OSC's 20 CPU-minute limit; FASRC's "not more than once a minute" polling rule).

## 6. The extension, per browser

WXT emits the Chrome/Edge MV3 service worker and the Firefox event page from one background entry and
the Safari build for Apple's packager. `browser.*` with Promises, no polyfill (the polyfill was archived
2026-07-30 and is a no-op from Chrome 148), `minimum_chrome_version: "148"`.

| Browser | Background | UI | Network contexts | Notes |
|---|---|---|---|---|
| Chrome, Edge | MV3 service worker; may hold a WebSocket alive with a ≤20-second ping only during the seconds-long bootstrap | `sidePanel` | content script for writes and the shell; service worker allowed for polling GETs after check 3 passes | a `fetch()` taking over 30 s kills the worker, which is one reason the bootstrap is short |
| Firefox | MV2 with a persistent background, or MV3 with alarms | `sidebar_action` | content script for everything | `port.onDisconnect` is routine: message ports cannot keep an event page alive |
| Safari | assumed to die within tens of seconds | popup or a pinned extension tab | content script for everything | per-site prompt on first visit; see `MAC_AND_SAFARI.md` |

The `alarms` API enforces the ≥60-second scheduler-facing floor by construction, since Chrome will not
honour periods under 30 seconds. `storage.local` holds the portal hostname and granted origin,
preferences, the acceptance record, the licence key and institutional identifier, the audit log, the
last good kill-list, a random installation identifier, copies of error reports and the ticks on the
optional checklist steps; `storage.session` holds connection state (job number, session name, the
session's claude.ai link) and this session's acknowledgement of the data disclosure; there is no
durable secret (`PRIVACY.md` and `SECURITY.md` carry the same list; the report's own sentence names
four items and says "only", but the licence key, the audit log and the last good kill-list that its
security controls also require are durable, so the list here is the complete one). The content script is registered
programmatically with `scripting.registerContentScripts` for the one granted origin after the
click-time grant, because the host is not known at build time. Messages are accepted only after
checking `sender.id`.

## 7. Security controls

From the report's "Security controls", in the order a reviewer will look for them.

- **One origin, granted at click time.** No install-time host permission; the single portal origin is
  requested from a button handler. A malicious update therefore inherits one origin per user rather
  than "all sites". Universities can confine it further with Chrome's
  `ExtensionSettings.runtime_blocked_hosts` and `runtime_allowed_hosts`; the exact host and permission
  list is published so a security office can set them.
- **No `cookies` permission.** The portal cookie is used by the network stack and never read.
- **No script on claude.ai.** The only content script is on the portal origin, which removes the
  DOM-injection and prototype-skimming classes for everything except the portal page itself. The
  extension never stores a credential and never touches the MFA approval step.
- **One chokepoint.** Every portal request passes through one function that appends an append-only,
  on-device audit record (UTC time, endpoint, method, job id, byte count, outcome), viewable and
  exportable by the student and never transmitted, and enforces the poll floor and the shell
  single-use rule.
- **Signed kill-list, fail-safe.** Once a day the service worker fetches a signed JSON document
  (permitted because JSON is data), verifies it with `crypto.subtle.verify` (Ed25519; ECDSA P-256
  fallback below Chrome 137, Firefox 130 and Safari 17) against a public key compiled into the
  bundle. A revoked version refuses to send commands and tells the student why. Offline, the last good
  list applies; the extension refuses only on a verified revocation, so an outage of a one-person
  vendor does not strand a campus. Licence revocations travel in the same document.
- **Per-job token.** The worker carries its own random token so that a request reaching the proxy with
  a valid portal session cannot drive another student's worker (the `/rnode/` handler does no job or
  ownership lookup).
- **Release pipeline.** Lockfile and `npm ci`; actions pinned by commit SHA; a build attestation from a
  hosted builder (SLSA level 2 at minimum, signing material inaccessible to build steps as the level 3
  target); reproducible-build instructions published for all stores; no long-lived store API key in CI;
  publisher account and kill-list signing key behind a hardware security key with no third-party OAuth
  grants.
- **Cluster side.** Supervised mode by default; the task manifest (working directory, allowed
  partitions, allowed egress hosts) enforced by the framework independently of the agent; input data
  read-only with a separate writable working directory; scheduler polling never faster than the
  profile's floor; tokens never on command lines, in argv, in logs, in job files or in
  `sbatch --export`.
- **Nothing deleted outside the run directories.** The framework removes only what is under its own
  `<shared_state_dir>/<run>/` and the job's node-local temp and `/dev/shm` directory; never the Claude
  Code login directory, the workspace, another run or anything else under `$HOME`. A destructive
  subcommand refuses when `CLAUDECODE`, `ASHLEY_REQUEST_ID` or a similar agent marker is in the
  environment, or when stdin is not a terminal. Added after the incident of 2026-09-28 (`SECURITY.md`).
- **Claude Code's settings file, two keys.** `<claude_config_dir>/.claude.json` is read for
  `remoteDialogSeen` and the workspace's `hasTrustDialogAccepted` only, and rewritten only to seed
  `hasCompletedOnboarding`, `theme` and that trust key, only when the student has started a login or a
  worker on purpose. The credentials file beside it is never opened.

The data disclosure the extension shows at first run and at each job start, in the report's words:
files the worker reads and every command's output are sent to Anthropic; while you are connected
through claude.ai the transcript is also stored on Anthropic's servers; a personal plan is retained
five years if model training is on and 30 days otherwise; no BAA covers a personal plan; FERPA records,
IRB data and export-controlled technical data must not be in the working directory; Remote Control
usage draws from your plan's shared limit. The extension refuses to start in a directory the student
has marked restricted, and when the CLI reports Remote Control unavailable under Zero Data Retention.

## 8. Discovery

Phase 1 runs on the login node through the bootstrap shell, one command batch, under a second of CPU
and no network: `command -v` for the scheduler CLIs, `module -t avail` filtered for
apptainer/singularity/podman/enroot, `srun --help | grep -c container-image` for Pyxis,
`sysctl -n user.max_user_namespaces`, the proxy and temp environment variables, one
`sinfo -h -o '%P|%l|%a'`, `/etc/os-release` and `ldd --version`. Phase 2 is one five-minute probe job
on the default partition that prints the node-local temp and `/dev/shm` sizes, tests
`apptainer exec docker://alpine true` (registry egress and user namespaces together), runs the
`curl -m 10` matrix against the three Anthropic hosts with and without the inherited proxy variables,
and runs `claude --version`, `claude auth status` and a short `claude remote-control` dry run inside the
image. The probe is not optional: TACC hides the Apptainer module on login nodes, so `module avail` is
negative there while the runtime exists. A documentation-derived profile is kept as a seed only; for
eight of twelve sampled sites the documentation was silent on at least one of egress, runtime version
or temp size, and the probe overwrites it.
